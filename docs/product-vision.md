# ChangeCheck 完整产品形态（Product Vision）

> 最后更新：2026-10-07 ｜ 上游文档：project-brief.md（决策与 v1 范围以主文档为准，本文描述完整形态与演进路线）

## 0. 一句话

ChangeCheck 的完整形态是 **"AI 功能的验收层"**：介于"我改了"与"我上线"之间的一道理化质量门——就像 CI 之于传统代码，它之于 AI 功能。

## 1. 三种产品形态（同一内核，按用户成熟度递进）

### ① Web 工作台（新手入口 = 比赛 v1）
四步向导：描述任务 → 准备测试 → 配置两版本 → 运行看报告。
价值主张：第一次有人教新手把"别瞎编时间"变成可执行的验收规则。

### ② CLI + CI 守门（日常习惯形态）
```bash
changecheck run --baseline v1 --candidate v2
# 关键验收不通过 → 非零退出码，阻断合并/部署
```
- 测试集与验收标准以 YAML 存仓库、随代码版本化
- 接入 GitHub Actions / GitLab CI：改提示词的 PR 必须先过验收
- 意义：产品从"工具"升级为"流程"

### ③ MCP/SDK（Agent 原生形态）
- 暴露 MCP server，AI 编程代理（ZCode/Claude Code 等）改完提示词后**自己跑验收、读退步报告、修复后再交付**
- 直接闭环 v1 亮点"报告可交给 AI 编程工具继续修"——从导出文件升级为机器可调用

## 2. 内核五层结构

| 层 | 完整形态 | v1 起点 |
|---|---|---|
| 测试资产 | 会长大的测试集：手工 / AI 草稿(人工确认) / 真实错误转化 / 生产回流(Langfuse/OTel)；打标、去重、版本化 | 手动导入 + 比赛种子集 |
| 验收标准 | 检查项 → 规则库 + 参考答案 + AI 裁判(固定评分标准+抽样审计) + 采用条件策略("关键要求全过才采用") | 规则 + 参考答案 |
| 执行引擎 | 基线/候选版本对、并发批量、结果缓存、多次运行看波动、多 provider(GLM/DeepSeek/Ollama) | 两版批量调用 |
| 决策报告 | 总体+逐条、新增失败优先、字段级证据、采用/复核/拒绝三态、趋势回溯("该样例从 v3 开始挂") | 对比报告 + 导出 |
| 守门集成 | CLI/CI、MCP server、生产错误回流、Webhook | 无（报告导出为雏形） |

## 3. 演进路线

- **v1（比赛 4 天，2026-10-11 截止）**：Web 单场景（中文通知提取），规则+参考答案，对比报告可导出
- **v1.5（赛后数周）**：AI 测试草稿(人工确认)、AI-as-judge、分类场景模板、重复运行与波动分析
- **v2（数月）**：CLI+CI 门禁、配置进 git、生产错误回流、MCP server、测试集管理（标签/去重/趋势）
- **v3（愿景）**：场景模板包生态；**按用户验收标准做模型选型推荐**（"全过验收前提下最便宜/最快的模型"）；团队共享验收标准

## 4. 战略判断

1. **护城河在测试资产，不在执行引擎。** 用户积累的验收标准与回归测试集是迁不走的资产；一切演进围绕"让资产更容易长大"。
2. **北极星指标：上线前拦截的改版事故数。** 路演叙事：平均分上涨会掩盖新增失败，ChangeCheck 负责在上线前把退步钉出来。
3. **类比定位（对外话术）**："AI 功能的回归测试 + 验收单"——Vitest/pytest 管代码行为，ChangeCheck 管 AI 行为，且为不懂评测的人设计。

## 5. 信息架构（完整 Web 版，供 v1 留扩展口）

- 任务（场景）列表 → 任务详情（验收标准 + 测试集两个 Tab）
- 版本管理（基线/候选，配置 diff）
- 运行记录 → 单次报告页
- 设置（provider、定价表、采用条件策略）
- v1 只实现：单任务 + 测试集 + 一次对比运行 + 报告页，但数据模型按上述分层设计（run 与 task 分离、规则结构化存储），避免返工。
