ChangeCheck · 改版验收官

AI 功能的回归验收层 —— 改了提示词、换了模型之后，用证据回答：哪些变好了？哪些被改坏了？这次改版值不值得上线？

0. 三十秒看懂

AI 功能的迭代方式是改提示词、换模型、调流程——这也是所有软件里回归风险最高的一类改动：输出不确定、无法断言，个人开发者只能改完自己试两三条、看着流畅就上线。一次「好心」的改版（比如要求输出更完整），模型就开始给没写的字段编造 18:00、给"另行通知"编造截止时间——而平均观感还在变好，新增的坏被完全掩盖。

ChangeCheck 把它变成一道有证据的验收工序：业务要求 → 可确认的检查项 → 回归测试集 → 两版本对比运行 → 新增失败优先的验收报告。传统代码有 CI 挡回归，AI 功能此前没有——ChangeCheck 补上这一层。

1. 背景与痛点

LLM 应用已进入"频繁改版"阶段，但没有配套的回归验收手段。 接入大模型的功能（问答、提取、分类、生成）在上线后会被持续修改：调提示词、换更便宜的模型、改流程。每一次修改都是对"AI 行为"的全量改动——没有任何测试覆盖改后的行为，因为输出是不确定的。

现状做法与代价：

  • 肉眼抽样：改完自己试 2–3 条输入，看着不错就发布。样本外的行为变化未知。
  • 平均分误导：即使做了评测，大家看的也是平均分/通过率——平均分上涨完全可能与"某类输入出现新增失败"同时发生。
  • 错误不积累：线上发现一条坏输出，反馈给开发者看一眼就过去了，不会沉淀为回归用例；同一个错误在下次改版后复发。
真实复现（本项目实验数据，非虚构）：我们用 DeepSeek（deepseek-flash）做了两组实验——
① 植入缺陷演示：把稳定提示词改成"输出更完整可用、未写字段给合理默认值"（一个典型的好心改版）。结果候选版 36 条样例全部出现关键违规：给"具体时间另行通知"补 18:00、给未定地点填"待定"、把"下周五"擅换成具体日期，且费用 +215%、耗时 +205%。
② 盲测：改用一个看似无害的"精简提示词省 token"版本（未预埋任何缺陷，结果事先未知）。工具真实抓出 8 条新增失败（8 条关键违规）：因删掉"date/deadline 区分"规则导致 5 条样例的日期错误落入 deadline 字段、给"延期待定"补字面"待定"——而且更贵 +73%、更慢 +81%（指令模糊使思考型模型消耗更多推理 token）。"以为省了钱，实际又贵又坏"，只有逐条证据能揭示。

3. 应用场景

3.1 首发场景：中文通知结构化信息提取（已完整实现并验证）

"通知转待办/日程"类功能：从中文通知中提取活动名、日期、时间、地点、截止时间。字段与值明确可机器核验、错误一眼可见。内置 36 条四类种子测试集（正常/缺失/歧义/对抗），开箱即可复现本页所有实验数据。

3.2 同构扩展场景（数据模型已预留）

  • 客服/工单分类：改提示词后分类错误率是否在某类工单上恶化（枚举字段 + 参考答案模式相同）
  • 文档问答/摘要：关键信息是否漏答、是否开始编造（要求引导生成"必须包含/禁止编造"检查项）
  • 任何"输入文本 → 结构化输出"的 AI 功能：任务 schema 与检查规则均为数据驱动，新增场景不改内核

3.3 目标用户

已在产品中接入 AI 能力的个人开发者与小团队：不想搭建评测平台、不会写评测 YAML，只想在改版上线前知道"有没有改坏"。对比之下，promptfoo/DeepEval 面向会写配置的工程师，Langfuse/Braintrust 面向有平台的团队。

4. 技术架构

单体 Next.js 应用 + SQLite（Node 内建 node:sqlite，零原生依赖）+ OpenAI 兼容 API + Docker Compose 一键部署。 关键设计是内核与 UI 解耦：内核三层不依赖 Next/React，为 v2 的 CLI/CI 守门与 MCP server（AI 编程代理自跑验收）直接复用而设计。

层组件职责与要点
内核（自研）执行器 executor并发批量调用、重试退避、单次调用硬超时、用量/费用/耗时逐条记录、多次重复 + 多数决（吸收 temperature=0 下的真实波动）
检查器 checkerJSON/schema/字段级规则：缺失必须留空（凭空补全恒为关键违规）、必须提取、逐字一致（含数字保护，防"10月1日⊂10月17日"假近似）、事项名等价放宽；规则全部经 21 项单元测试固定
回归报告 report新增失败优先、关键违规标红、分类统计、费用/耗时对比、三态结论（含 punchline 叙事）、Markdown 导出；逐条证据存 run_items，报告可追溯

UINext.js App Router四步向导（验收标准→测试集→版本→报告）；无 key 可用 mock 模式跑通全流程

5. 创新点小结

  1. 回归优先的验收报告（行业空白）：以"这次改版新增了哪些失败"为第一视图，证据链到字段级——违反哪条要求、期望/实际值、原文依据；平均分叙事被明确替换为反差叙事（"费用 -68%，但有 8 条新增失败"）。
  2. 要求引导引擎（把 promptfoo 红队已验证的"自然语言→用例"交互迁移到业务质量域）：不懂评测的人用一句话描述要求，得到可确认的检查项；冲突检测在引导阶段就拦截"为完整而补全"这类高发事故源。
  3. 零运维的测试资产积累：线上坏输出一键入库为回归用例，测试集随产品长大——这是用户迁不走的资产，也是本项目主张的护城河（执行引擎是 commodity，验收资产不是）。
  4. 中文优先与国产模型一等公民：中文断言细节（数字/日期保护、命名等价、全半角归一）、全中文产品与报告、OpenAI 兼容直连 DeepSeek/GLM/Kimi——搜索确认的完全空白带。

6. 开源治理

  • MIT 协议，无厂商背景的中立开源；依赖极简（运行时仅 next/react/react-dom，数据库用 Node 内建模块）

  • 隐私与安全边界明确：key 只走环境变量；所有数据本地存储
