## 1. 一句话定位

帮助**缺少评测经验的个人开发者**，把业务要求变成**可重复运行的测试**，再用**证据**判断一次 AI 功能改版（换提示词/换模型/改流程）的得失：哪些变好了、哪些原本正常的功能被改坏了、这次改版是否值得采用。

- 产品形态：独立 Web 应用（v1 不依赖、不包裹任何现有评测平台）
- 首个演示场景：**中文通知结构化信息提取**（如"通知转待办"：提取活动名/日期/地点/截止时间）
- 目标用户：已在自己的产品里接入 AI 功能的人（AI 问答、信息提取、分类、生成类应用开发者）

## 3. 关键决策记录（ADR）

### D1 ｜ 放弃视频项目主线，转向验收工具
原持有"AI 视频生成+剧本"项目。放弃主投原因：开源竞品 Toonflow 已占"剧本→分镜→成片一体化工作台"定位（含角色一致性管理），"简单组合"风险高。评测工具方向为赛道解读点名征集，且与 Toonflow 零撞车。
**视频项目保留为回退方案**（见 §7 回退线）。

### D2 ｜ 差异化定位（vs Langfuse / Promptfoo）
两者已支持实验对比、逐条退步查看、费用耗时比较（Langfuse）、批量提示词/模型比较（Promptfoo），"两边回答并排展示"不构成亮点。护城河三件事：
1. **要求引导引擎**：把自然语言业务要求（"别瞎编时间"）引导成用户可确认的检查项 + 规则 + 各类样例（正常/缺失/歧义/对抗）
2. **回归导向报告**：新增失败优先展示，说明违反哪条要求、影响哪个字段、证据在哪；报告可直接交给 AI 编程工具继续修
3. **测试集积累**：真实错误 → 加入测试集 → 每次改版复跑，检查是否复发

### D3 ｜ 从零实现，Langfuse 不进代码库
- 不 fork Langfuse：自托管需 Postgres/ClickHouse/Redis/对象存储整套设施，4 天工期养不起；fork 换 UI = "套壳"，技术创新维度自杀；仓库 ee/ 目录为专有许可，fork 有合规坑；其架构（运行时 tracing/团队 prompt 管理）与本品形态错配
- Langfuse 的三个正确用法：① 文档中作"相关工作"对比（技术创新答卷）② 路线图素材（v2 通过其 API 把线上错误自动转测试样例 → 喂"长期发展 20%"）③ 演示对照镜头（时间富余才做）

### D4 ｜ v1 范围
**做**：中文通知提取任务模板 / 样例导入·编辑·人工确认 / 两版本（提示词或模型）批量运行 / 字段级规则检查 + 新增失败定位 + 费用耗时记录 / 可导出对比报告 + 可复现示例数据
**砍**：AI 辅助评分（AI-as-judge 延后）/ AI 生成测试草稿（v1 手动导入）/ Langfuse 对接 / 多场景（分类、文档问答等后续扩展）

### D5 ｜ 首场景 = 中文通知信息提取
理由：字段与值明确可机器核验、错误一眼可见、评审零解释成本。场景难度梯度（后续扩展序）：文本→结构化提取（最适合）> 分类 > 文档问答 > 主观生成 > 多步智能体。

### D6 ｜ 被测模型 = DeepSeek（OpenAI 兼容 API），已有 key（2026-10-07 定）
- M0 与 v1 的被测调用走 DeepSeek，OpenAI 兼容协议（baseURL `https://api.deepseek.com`），key 由环境变量 `DEEPSEEK_API_KEY` 注入，**不落仓库**。
- M0 实际使用 **deepseek-flash**（用户指定，思考型模型）；两版本**同模型、不同提示词**对比（隔离变量）。执行器按协议实现，换模型/GLM/Kimi 只改环境变量。
- 注意（M0 实测）：思考型模型必须给足 max_tokens（≥2000），否则思考耗尽额度、正文为空。

## 4. 产品设计

### 用户流程（四步）
1. **描述任务**："从通知中提取活动日期；原文没写的信息必须留空。"
2. **准备测试**：导入样例与参考答案，人工确认（v1 核心打磨点：引导成检查项——必须提取什么？何时留空？绝不能凭空补什么？格式约束？哪类错误零容忍？）
3. **配置两版本**：旧版/新版的提示词、模型及参数
4. **运行并看结果**：总体变化 + 逐条退步 + 费用耗时 + 导出报告

### 核心演示案例（通知提取）
输入："请于 10 月 12 日提交实验报告，具体提交时间另行通知。"
- 正确要求：提取日期；具体时间**留空**
- 旧版：时间留空 ✓ ｜ 新版：补了"18:00" ✗（违反"缺失必须留空"）
- 报告单独展示该案例：错误字段 + 原文依据 + 违反规则 → 证明"改版不能只看回答流不流畅"

### 报告设计
总体表（通过率/费用/耗时对比）+ 展开后：新增通过 / **新增失败（最优先）** / 其中违反关键要求的案例单独标红。采用条件由用户事先设置（如"关键要求必须全部通过"），报告保留"需人工确认"状态。
示例（假设数字）：旧版 45/50 通过、¥2.00、2.4s；新版 46/50、¥1.20、1.7s —— 但含 2 条新增失败，其中 1 条违反关键要求 → 结论："整体更省更快，但有新增失败且涉及关键要求，建议复核后采用。"

### 检查方式（v1 只做前两种）
| 方式 | 用途 | v1 |
|---|---|---|
| 程序规则 | 格式/必填/数字/日期/枚举/留空 | ✅ 核心 |
| 人工确认参考答案 | 固定对照 | ✅ 核心 |
| AI 辅助判断 | 语义要求 | ❌ 延后 |

对比铁律：相同输入、相同参考答案、相同评分规则；记录两版本配置；重要样例可重复运行；费用按返回用量估算，缺用量标"未知"。

### 参赛亮点（写进介绍文档）
1. 自然语言要求 → 用户可确认的检查项
2. 面向改版的错误报告（新增失败优先、可交给 AI 编程工具继续修）
3. 测试可积累（真实错误 → 回归用例）
配一个完整改版故事：旧版稳但慢 → 新版省但埋雷 → 工具抓出 → 修复 → 复跑确认消失。

## 5. 技术方案

- **栈**：Next.js 单体 + SQLite（零外部依赖）+ DeepSeek OpenAI 兼容 API（已定，见 D6；执行器协议兼容，可零成本换 GLM/Kimi 等）+ Docker Compose 一键运行（评审可直接验证）
- 自研三层（评审可识别的"非套壳"部分）：要求引导引擎 / 执行器（并发调用、用量与耗时记录、重试）/ 回归报告
- 调用量估算：50 样例 × 2 版 × 3 次 = 300 次被测调用（提取任务、小模型，成本几元级，不构成约束；先用 10 条跑通再扩全量）

## 6. Milestone 0 —— 验证实验（✅ 2026-10-07 完成，含真实 API 全量数据）

**要回答的问题**：用一小批明确样例，能否准确找出一次真实改版引入的新错误？

**答案：能，且零误报。** 最终真实跑（deepseek-flash，36 样例 × 2 版 × 3 次 = 216 调用，报告 `m0/out/report-real-20261007131433.md`）：

- **植入退步 36/36 全部抓到**：新版（"更完整可用"提示词）0/36 通过、36 条关键违规——缺失字段凭空补 18:00/待定、相对日期擅换算、改期干扰日期采信、原文表述改写，全部被字段级规则逐条钉出
- **稳定样例 0 误报**：旧版 36/36 通过；temperature=0 下 2 条样例各有 1/3 次波动，被"3 次重复 + 多数决"吸收（→ 执行引擎默认行为）
- **成本/耗时对比可用**：旧版 ¥0.199/1190ms vs 新版 ¥0.823/4630ms（新版更慢 ~4 倍更贵 ~4 倍还更差）——"平均分上涨会掩盖新增失败"的路演叙事有了真实数据
- 经典案例 M01 与 §4 预测完全一致：新版 3/3 次补出 `time:"18:00"` + 编造 deadline

工程发现（详见 m0/README.md）：思考型模型 max_tokens 截断坑、event 命名匹配放宽、参考答案人工标定环节、复跑多数决——直接进 v1 执行器/引导引擎设计。

产出三用：✅ 场景落地 30% 的验证数据（真实环境）｜✅ 产品种子测试集（36 条，含参考答案与检查项）｜✅ 路演故事线（有真实报告与原文证据）
